# Ticket workflow

The steps around `/implement <ticket>`, in order. Each ends on the condition that says it's done.

A `ready-for-human` ticket run against a live league follows `docs/agents/live-run.md` instead, and ends at its results comment: each fix it finds is a `ready-for-agent` ticket, built in a fresh session. #110 ran and fixed in one session and ended at 173k.

## 1. Glossary first, before the first test

Before reading code, list what the ticket adds. If it adds two or more commands or behaviours with their own seams, propose a split once, naming the line to cut on. Size alone is no reason, and a ticket's "Size watch" section is no reason either: #55 and #60 were split, and each part still ended well over the 150k zone while paying for its own review and sweep.

List every domain noun the ticket's text uses, or the build brings or renames, that `GLOSSARY.md` has no heading for: a file, a setting, each value a setting can take, a role, a command, a state. `grep -n '^\*\*' GLOSSARY.md` lists the headings in about 1k; grepping the whole glossary for the ticket's words cost #69 8k. In #69, "player fact" was in the ticket's title and body, and step 1 reported no new noun until the standards review caught it. `test/glossary-terms.test.ts` checks dashed values such as `losers-bracket` too: in #61 part (a), `most-bench-points` carried the _Avoid_ term "bench points" into `league.md`. Run `/domain-modeling` for each one that `GLOSSARY.md` doesn't define, at the same time as agreeing the test seams. Then name files, fields and functions after the glossary terms.

Read the ticket with `gh issue view <n> --json title,body,comments --jq '.title, .body, (.comments[-1].body // "")'`, and the spec sections it cites: triage posts the Agent Brief, with its criteria and the maintainer's decision, as the latest comment. When the user names another comment, read that one, not the whole thread. In #90 the whole thread came in with this file, 6.4k. To find where a neighbouring ticket's scope begins, ask an Explore subagent for a short brief rather than reading the ticket. To find code, start from the module map's exports column and read only the functions you need, not whole files. Grep the map for the functions, files, glossary nouns and commands the ticket names, and for the test seam it touches (`grep -n -i -E 'checkDraft|evidence pack|\*\*CLI\b' docs/agents/module-map.md | cut -c1-200`; a hook refuses it without the `cut`), matching each row by its name, never by its bullet, rather than reading it whole. Grep a function or file by its backticked name (`` `fetchOrContinue` ``): in #90, bare `snapshot` and `refresh` pulled in three pipeline paragraphs where two rows were used; read it whole only when nothing matches. In #94, a new command named only by behaviour and nouns, the whole map cost 11.7k and five rows plus the CLI seam were used. In #82, #84 and #72 the whole map was the largest read (about 10k), and #82 used two rows, one pipeline line and one seam bullet.

Done when the list is in a message, each noun with its `GLOSSARY.md` line or a new entry. A ticket with no new noun still gets the message: one line naming the glossary terms its user-facing text uses, and any phrase in that text the glossary doesn't define. In #82 the step was skipped, and the error's "snapshots folder" and "season folder" went in undecided, since the glossary test checks only _Avoid_ terms. The code and tickets then use those names from the start. In #51 the glossary came last, which forced a code rename (`usage.yaml` → `spend.yaml`) and a second pass over 10 tickets and comments.

A brief line the build would meet only loosely (a wording, a path form, an exit code): ask in this message, beside the list, rather than recording the choice in the commit. In #118 the brief's "its path as the CLI shows paths" went in workspace-relative as a "known choice", and after the sweep the maintainer asked for the CLI's paths: a second commit, about 15k.

## 2. Build and review

`/implement`: TDD at the agreed seams, then `/code-review` in two subagents, then commit to `main`. A seam the ticket names is agreed; ask before testing at any other. See each new test fail before writing the code that passes it. For a test of code that already exists, committed or written earlier in the build, see it go red with `npm run -s mutate -- <src-file> '<old>' '<new>' <test-file>`: it changes one place, runs that test file, prints the tests that went red (or "survived", exit 1, or "not tested", exit 3, when the test file didn't load) and puts the file back. Copy `<old>` from the file as it stands after `npm run -s format`: in #125 the formatter had rewrapped `LOSS_VERB`, and an `<old>` copied from the edit matched nothing. A mutation changes the code as built, and the build never widens what shipped code accepts just to give a mutation something to change: pick a mutation of code that exists, spanning several lines if it must. In #129, widening the count regex to decimals so "a decimal counted as a count" had a target made "2.0 high scores" a rule's count, out of scope; only the spec review caught it. Run each `mutate` call alone in its Bash call, quoting each `<old>` and `<new>` on its own: in #59 part (b), a loop that split pairs on `|` broke on the code's `||`, and `.claude/hooks/mutate-one.sh` refuses a command that chains, pipes or adds a line beside it. It edits the file in the working tree, so run it before launching the reviews or after both have reported. In #89, two mutations ran during the spec review, and its scratch tests saw 5 failures it couldn't explain. In #77, nine mutations by hand (Edit, test run, `git checkout`, re-Read) cost about 25k. In #60 part (b), the checklist tests were written with their code and first seen red only by a mutation after the build.

Before the first test, read the case file in `docs/agents/workflow/` for each case the ticket touches:

- A change to `src/validator.ts` or `src/validator/`: `validator.md` (`claims:diff` before the reviews).
- A new error or warning, or a new state reaching an existing one (a new reason, transport or environment variable): `messages.md`.
- A new `drive-wizard.exp` scenario, or a change to a wizard prompt (`cli.ts`) or a setup step (`init.ts`): `wizard.md`.
- A change to a style page (`style-pages.ts`): `style-pages.md`.
- A ticket that says to diagnose before choosing a fix: `diagnose.md`.
- A change to a helper in `test/support/`, or one that adds something to every draft's output: `test-helpers.md`.
- A change to `package.json`'s `bin`, `files`, `dependencies` or `scripts`, to `src/cli.ts`'s entry, or to `scripts/release.ts`: run `npm run -s install:smoke` (about 20s) before committing, since CI runs it only after the push and the pre-commit hook doesn't.

A pasted `/implement` arrives as text, and the skill can't be loaded with the Skill tool, so read `~/.claude/plugins/cache/mattpocock/mattpocock-skills/*/skills/engineering/implement/SKILL.md` directly. In #56 part (b), searching for it with `find` cost 7.4k.

Add to the spec subagent's brief: "Run the built library in scratch scripts: the ticket's commands in sequence, and each failure after a command has begun writing. Write each run as a script file in the scratchpad that starts with `set -euo pipefail` and sets `HOME` and the working directory to a temp folder, and `LAZY_PUNDIT_REPLAY` to a fixture snapshot, so no request leaves the machine. Drive `init` with `npm run -s drive:wizard:plain -- <scenario>`, adding a scenario if yours is missing. For `refresh`, make the data change with a patched replay, so the run reaches the data-changed path. A run that needs a patched replay or another `test/support/` helper can be a `test/scratch-*.test.ts` file (gitignored), run from the repo root with `npx vitest run <file> --silent=false`, since a passing test's console output is hidden otherwise; delete it before you finish." In #101 the spec review rebuilt `dist` and re-blobbed the replay by hand for that patch (67k against the standards review's 45k), where a scratch test file did it in about 2k. In #73 the spec review's `refresh` runs replayed week 9 over a week-8 draft and got "No changes", so the path that edits the front matter went unrun. For a criterion that output stays as HEAD's, save HEAD's output to the scratchpad before the first edit and give the spec review those paths to diff against: in #107 the brief didn't name them, and the review copied HEAD's script into `scripts/` to rebuild them.

The same script rule holds for your own scratch runs. In #60 part (a), a one-liner's failed `cd` left its `mkdir` and `touch` running in the repo. A scratch run calls the library with `node`, which strips the types, or uses `npm run fixture:show`, or is a `test/scratch-*.test.ts` file as in the spec brief above, deleted before launching the reviews. In #56 part (a), a vitest run outside the repo root hung past its timeout.

See each review fix's test go red, by writing it before the fix or by undoing the fix. Tighten any test that stays green. A review fix that adds behaviour gets its own scratch run through the ticket's commands before committing, since no review sees it. A write that has to fail gets a test that chmods its file or folder, skipped on Windows and as root (`test.skipIf(process.platform === "win32" || process.getuid?.() === 0)`, as in `test/style-pages.test.ts`), since CI's ubuntu runner isn't root. A fix that no test can show failing gets a scratch run that shows it instead, named in the commit message. Done when every fix has a test seen red, or that scratch run, and each added behaviour has had its run. In #55 part (a), one of six fixes' tests stayed green: it missed the snapshot a late failure leaves behind. In #55 part (b), a warning added after review misfired on auto-tagged stats, and only the sweep's scratch script caught it.

While building, run `npm run -s format` (it fixes formatting itself and fails on any other lint problem) with the typecheck, and the affected test files plus `test/glossary-terms.test.ts` and `test/module-map.test.ts`, which check every new comment and module. In #47 part (a), both failed only after the build was done; in #79, lint failed only at the commit. The commit's pre-commit hook runs typecheck, lint and the full suite, and that is the final full-suite run. A change a tester would notice (a `check` reading, a message, a command) adds its line to the next release's `CHANGELOG.md` entry in the same commit, worded for testers: #128 left it out, and 0.1.2's entry missed its fix until the retro after #129. Write the commit message with the Write tool to a scratchpad file, then run `git commit -F <file>` as its own command; a hook refuses an inline message, and #101 wrote its message twice.

A flaw you'd hand the reviews as a known issue: fix it before launching them when the fix fits the ticket. In #98, "Fetching the league… prints before the refusal" went to review as cosmetic, and both reviews' fixes moved the refusal out of `checkLeague`. The same goes for a shortcut that narrows a rule the brief states (a cap, a pruned search, a heuristic): before the reviews, write a test for each case the narrowing could drop. In #93 the hint search was pruned for speed, timed only on a fault no fix mends, and handed to the spec review as a question; it found three combinations the pruning hid, a second red-green round of about 20k.

## 3. Sweep the tickets in one subagent

After the commit, hand the sweep to one subagent, so the main session doesn't spend tokens reading tickets. Give it the prompt in `docs/agents/sweep.md`, with the blanks filled.

Done when the subagent's report accounts for every open ticket, and the main session has asked the user, for each unowned item, whether to fix it here, file it as a ticket or leave it, with a guess at each fix's size. A fix here that adds a state or an option counts a spec review in its size, since no review saw it otherwise: #118's e7e5d7f added both, unreviewed. A ticket filed for one holds what happened and how to reproduce it, and triage writes its options and criteria: #128 was filed with both, and its triage minutes later replaced them. In #119, a file-or-leave question was rejected for "can we do the quick ones here". In #56, the changed-outcome warning in `check` and `publish` was left undone by both parts, and #56 was closed with no ticket owning it.

## 4. Measure

Run `/context` and compare it with the 150k smart zone, run `npm run trace` for where the context went, then run `/retro`. The user pushes `main` (`! git push origin main`); `git push` is blocked for agents. After the push, run `gh run watch` (or `gh run list --limit 1` once it's done) and report the CI result.
