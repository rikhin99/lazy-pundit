# Ticket workflow

The steps around `/implement <ticket>`, in order. Each ends on the condition that says it's done. The incident behind each rule is in `docs/agents/workflow/history.md`: read it only when changing a rule.

A `ready-for-human` ticket run against a live league follows `docs/agents/live-run.md` instead, and ends at its results comment: each fix it finds is a `ready-for-agent` ticket, built in a fresh session.

## 1. Glossary first, before the first test

Before reading code, list what the ticket adds. If it adds two or more commands or behaviours with their own seams, propose a split once, naming the line to cut on. Size alone is no reason, nor is a ticket's "Size watch" section: split parts have still ended well over the 150k zone, each paying for its own review and sweep.

List every domain noun the ticket's text uses, or the build brings or renames, that `GLOSSARY.md` has no heading for: a file, a setting, each value a setting can take, a role, a command, a state. List the headings with `grep -n '^\*\*' GLOSSARY.md` (about 1k), and read only the entries the ticket's nouns name, each by its heading (`grep -n -A2 '^\*\*Award\*\*' GLOSSARY.md`), never a line range. `test/glossary-terms.test.ts` checks _Avoid_ terms, dashed values such as `losers-bracket` too, but not undecided names. Run `/domain-modeling` for each noun `GLOSSARY.md` doesn't define, at the same time as agreeing the test seams. Then name files, fields and functions after the glossary terms, since a late glossary forces renames across code and tickets.

Read the ticket with `gh issue view <n> --json title,body,comments --jq '(.comments | map(.body)) as $c | ($c | map(test("## Agent Brief")) | rindex(true)) as $i | .title, (if $i then (.body | split("## Input from")[0]) else .body end), $c[($i // -1):][]'`, and the spec sections it cites. Triage posts the Agent Brief, with its criteria, as a comment; the command prints it and every comment after it (the maintainer's decisions and later Input sections), or the latest comment when there's no brief, since a decision can come after the brief. With a brief, it leaves out the body's Input sections, which the brief supersedes: read one by its heading only when the brief names it. When the user names another comment, read that one, not the whole thread. To find where a neighbouring ticket's scope begins, ask an Explore subagent for a short brief rather than reading the ticket.

To find code, start from the module map's exports column and read only the functions you need, not whole files. Grep the map for the functions, files, glossary nouns and commands the ticket names, and for the test seam it touches (`grep -n -i -E 'checkDraft|evidence pack|\*\*CLI\b' docs/agents/module-map.md | cut -c1-200`; a hook refuses it without the `cut`), matching each row by its name, never by its bullet. Grep a function or file by its backticked name (`` `fetchOrContinue` ``), since a bare word pulls in pipeline paragraphs; read the map whole only when nothing matches.

For a split ticket's later part, run each owed item at HEAD (a scratch run) before the first test: an item HEAD already does needs tests only.

Done when the list is in a message, each noun with its `GLOSSARY.md` line or a new entry. A ticket with no new noun still gets the message: one line naming the glossary terms its user-facing text uses, and any phrase in that text the glossary doesn't define. For a state where a glossary noun no longer holds, the message also lists each line `docs/agents/workflow/messages.md`'s grep printed, with its fix or "stays". For a new error or warning, it lists each state that reaches it, each with the test that will show it: in #138 the draft note's placeholder state had none until the standards review.

A brief line the build would meet only loosely (a wording, a path form, an exit code): ask in this message, beside the list, rather than recording the choice in the commit, since a choice the maintainer reverses after the sweep costs a second commit.

## 2. Build and review

`/implement`: TDD at the agreed seams, then `/code-review` in two subagents, then commit to `main`. A seam the ticket names is agreed; ask before testing at any other. Write each output value a test expects from where it comes from, before the first run: a fixture value (a team's name, a record) from `npm run -s fixture:show -- <week> --model`, a CLI or plain-text line from a scratch run of the command. A guessed literal costs a red run to correct.

See each new test fail before writing the code that passes it. For a test of code that already exists, committed or written earlier in the build, see it go red with `npm run -s mutate -- <src-file> '<old>' '<new>' <test-file>`: it changes one place, runs that test file, prints the tests that went red (the first five, then a count; or "survived", exit 1, or "not tested", exit 3, when the test file didn't load or no test ran) and puts the file back. For a guard, where one test has to go red, add its name as a fifth argument (vitest's `-t`), or the output lists every red test. Copy `<old>` from the file as it stands after `npm run -s format`, which may have rewrapped it. A mutation changes the code as built: pick a mutation of code that exists, spanning several lines if it must, and never widen what shipped code accepts just to give a mutation something to change. Run each `mutate` call alone in its Bash call, quoting each `<old>` and `<new>` on its own: `.claude/hooks/mutate-one.sh` refuses a command that chains, pipes or adds a line beside it. It edits the file in the working tree, so run it before launching the reviews or after both have reported.

Before the first test, read the case file in `docs/agents/workflow/` for each case the ticket touches:

- A change to `src/validator.ts` or `src/validator/`: `validator.md` (`claims:diff` before the reviews).
- A new evidence ID, or a new shape of one's value: `evidence.md`.
- A new error or warning, or a new state reaching an existing one (a new reason, transport or environment variable, or a state where a glossary noun no longer holds, as week 0 has no starting order): `messages.md`.
- A new `drive-wizard.exp` scenario, or a change to a wizard prompt (`cli.ts`) or a setup step (`init.ts`): `wizard.md`.
- A new or changed expect driver (`drive-wizard.exp`, `drive-table.exp`) or a scenario in one: `pty.md`.
- A change to a style page (`style-pages.ts`): `style-pages.md`.
- A change to how `setup lore` or `setup stakes` keeps the pundit's lines: `merge.md`.
- A ticket that says to diagnose before choosing a fix: `diagnose.md`.
- A change to `scripts/scrub-*.ts` or a committed fixture set: `fixtures.md`.
- A change to a helper in `test/support/`, or one that adds something to every draft's output: `test-helpers.md`.
- A change to `package.json`'s `bin`, `files`, `dependencies` or `scripts`, to `src/cli.ts`'s entry, to `scripts/release.ts` or `scripts/install-smoke.sh`: run `npm run -s install:smoke` (about 20s) right after the commit, before the sweep. It installs HEAD, so a run before the commit tests the code without your change. On a failure, fix it and amend: nothing is pushed yet. CI runs it only after the push, and the pre-commit hook doesn't.

A pasted `/implement` arrives as text, and the skill can't be loaded with the Skill tool, so read `~/.claude/plugins/cache/mattpocock/mattpocock-skills/*/skills/engineering/implement/SKILL.md` directly.

Add to the spec subagent's brief: "Run the built library in scratch scripts: the ticket's commands in sequence, and each failure after a command has begun writing. Write each run as a script file in the scratchpad that starts with `set -euo pipefail` and sets `HOME` and the working directory to a temp folder, and `LAZY_PUNDIT_REPLAY` to a fixture snapshot, so no request leaves the machine. `eval "$(npm run -s fixture:workspace -- <week>)"` enters a workspace already drafted at that week, with its replay set, the clipboard off and `$DRAFT` naming the draft; it sets the working directory to the workspace, so run the commands from there. Each script prints one line per check (`events after save: 1`, `port 4790 free`), never a page or file body, and the report names each script's path, so a rerun after a fix is one cheap call. Drive `init` with `npm run -s drive:wizard:plain -- <scenario>`, adding a scenario if yours is missing. Check what only a terminal shows (a width, bold) with `env -u NO_COLOR npm --prefix <repo> run -s tty -- <columns> <command>`, which runs it in a terminal of that width. For `refresh`, make the data change with a patched replay, so the run reaches the data-changed path. A run that needs a patched replay or another `test/support/` helper can be a `test/scratch-*.test.ts` file (gitignored), run from the repo root with `npx vitest run <file> --silent=false`, since a passing test's console output is hidden otherwise; delete it before you finish. For a change to a git hook or a check in `scripts/`, run it through the real git command in a scratch clone (`git clone` the repo into a temp folder, apply `git diff HEAD`, `npm ci` so the hooks install), never in this repo." For a criterion that output stays as HEAD's, save HEAD's output to the scratchpad before the first edit and give the spec review those paths to diff against.

The same script rule holds for your own scratch runs, since a one-liner's failed `cd` leaves the rest running in the repo. A scratch run calls the library with `node`, which strips the types, or uses `npm run fixture:show`, or is a `test/scratch-*.test.ts` file as in the spec brief above, run from the repo root and deleted before launching the reviews.

See each review fix's test go red, by writing it before the fix or by undoing the fix. Tighten any test that stays green. A review fix that adds behaviour gets its own scratch run through the ticket's commands before committing, since no review sees it. A review fix that moves a function or type to another module gets a `mutate` in its new place, named in the commit message. The same goes for a fix that folds copies of code into one function: a `mutate` at each place it now serves, and each test file it serves pins that function's output as a literal, never by calling the function. A write that has to fail gets a test that chmods its file or folder, skipped on Windows and as root (`test.skipIf(process.platform === "win32" || process.getuid?.() === 0)`, as in `test/style-pages.test.ts`), since CI's ubuntu runner isn't root. A fix that no test can show failing gets a scratch run that shows it instead, named in the commit message. Done when every fix has a test seen red, or that scratch run, and each added behaviour has had its run.

While building, run `npm run -s format` (it fixes formatting itself and fails on any other lint problem) with the typecheck, and the affected test files plus `test/glossary-terms.test.ts` and `test/module-map.test.ts`, which check every new comment and module. The commit's pre-commit hook runs typecheck, lint and the full suite, and that is the final full-suite run. A change a tester would notice (a `check` reading, a message, a command) adds its line to the next release's `CHANGELOG.md` entry in the same commit, worded for testers. Write the commit message with the Write tool to a scratchpad file, then run `git commit -F <file>` as its own command; a hook refuses an inline message.

A flaw you'd hand the reviews as a known issue: fix it before launching them when the fix fits the ticket, since both reviews will spend a round on it. The same goes for a shortcut that narrows a rule the brief states (a cap, a pruned search, a heuristic): before the reviews, write a test for each case the narrowing could drop.

## 3. Sweep the tickets in one subagent

After the commit, hand the sweep to one subagent, so the main session doesn't spend tokens reading tickets. Give it the prompt in `docs/agents/sweep.md`, with the blanks filled.

Done when the subagent's report accounts for every open ticket, and the main session has asked the user, for each unowned item, whether to fix it here, file it as a ticket or leave it, with a guess at each fix's size. A fix here that adds a state or an option counts a spec review in its size, since no review saw it otherwise. A fix here that changes a signature counts its call sites (`git grep -c`) in its size, and makes the repeated change with `npm run -s replace`. A fix here lands after the sweep, so before reporting, correct each section or comment the sweep wrote that the fix contradicts. A ticket filed for one holds what happened and how to reproduce it, and triage writes its options and criteria. Ask file-or-leave even for a quick fix: the user decides what joins this ticket. A ticket closed with an item unowned loses it.

## 4. Measure

Run `/context` and compare it with the 150k smart zone, run `npm run trace` for where the context went, then run `/retro`. The user pushes `main` (`! git push origin main`); `git push` is blocked for agents. After the push, run `gh run watch` (or `gh run list --limit 1` once it's done) and report the CI result.
